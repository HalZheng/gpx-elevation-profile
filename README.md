# Elevation Profile · GPX 骑行海拔剖面分析

一个专注骑行爬升的纯静态网站：把码表导出的 GPX 变成一张可缩放的海拔剖面图，
自动识别长坡、按坡度给曲线分段着色，并可按 Strava 标准给爬坡分级。

**所有 GPX 都在浏览器本地解析，不会上传到任何服务器。** 联网行为只有两处：
载入轨迹后自动向 OpenStreetMap（Overpass API）取回周边地名作标注，以及你主动点击
「获取校准海拔」时向 Open-Meteo 发送的坐标查询。

## 功能

| 模块 | 说明 |
| --- | --- |
| 海拔剖面 | 高亮折线 + 下方同色半透明渐变填充（形成体积感）；横轴默认公里，可切换为时间 |
| 自适应坐标轴 | 滚轮/拖拽缩放后，纵轴按「当前可见窗口」重新取整，短坡与长坡都看得清 |
| 交互 | 滚轮缩放横轴、拖拽平移、双击图表或点「重置缩放」还原；一键导出 PNG（2 倍分辨率、排除缩放滑杆） |
| 悬浮气泡 | 海拔（必选）、坡度（默认开）、速度、心率、踏频（默认关） |
| 异常修正 | 双向坡度限幅，把气压高度计的「阶跃」异常摊开成合理坡道，总爬升量不变 |
| 数据平滑 | 中值滤波 / 滑动平均 / 两者组合，窗口按米给定，不同采样密度表现一致 |
| 海拔校准 | Open-Meteo（Copernicus DEM GLO-90）按经纬度反查地形海拔，支持原始/校准/对比三种显示，随时可反悔 |
| 折线标注方式 | **三选一互斥，不共存**：不标注 / 按坡度 / 按爬坡等级。任一方式都是同一套视觉语言——线段变色 + 下方同色渐变填充，不使用纵向色带 |
| 坡度着色 | 按坡度区间分段着色，带**迟滞**与**过短段合并**（默认最短段长按总距离自动取值），呈现的是「持续一段的坡度」而不是逐点跳变；内置 3 套配色预设，也可自定义任意坡度区间与颜色 |
| 爬坡识别与分级 | 连续爬升段 + 间隙桥接合并 + 长度/爬升/坡度三重阈值过滤；按 Strava 标准评分分级（Cat 4–HC），未达分级的爬坡用灰蓝 |
| 沿线地名 | 载入轨迹后自动取回周边的区县、街道村庄、景点高校与商圈（OpenStreetMap），按「离路线有多近」筛选并标在图上；一次联网取全量候选，之后的半径/间距调整全在本地算；同名归并、起终点锚定、标签避让，点击地名可放大到该位置 |

## 部署

仓库已内置 `.github/workflows/deploy.yml`：推送到 `main` 后 GitHub 会自动
`npm ci && npm run build`，并把 `dist/` 发布到 GitHub Pages。

首次使用需在仓库 **Settings → Pages → Build and deployment → Source** 选择
**GitHub Actions**。

`vite.config.ts` 里 `base: './'`，打包产物使用相对路径，因此可以直接丢到
Netlify / Vercel / Cloudflare Pages 的任意子路径下，无需改配置。

## 算法说明

**异常海拔修正。** 气压高度计偶发「几秒内凭空升降十几米」的阶跃，换算成坡度远超任何
真实道路。阶跃比中值窗口更宽，平滑去不掉，因此先用双向 1-Lipschitz 限幅把阶跃摊开成
坡度不超过「最大可信坡度」的坡道——只重新分配升降发生的距离，总爬升量不变。

**长坡识别。** 以滚动坡度为判据找出持续爬升的连续区段，再对区段做两轮合并：跨越短暂
平路/缓下（间隔与中途下降都在阈值内），且合并后平均坡度不低于设定阈值（避免把整条
起伏路拉成一个大坡）；最后按最小长度、最小累计爬升过滤。

**Strava 分级。** 评分 = 长度(m) × 平均坡度整数%，需同时满足坡度 ≥ 3%：
≥8000 为 Cat 4，≥16000 Cat 3，≥32000 Cat 2，≥64000 Cat 1，≥80000 为 HC。

**暂停压缩。** 等红灯、补给休息会让时间轴出现长段停滞：骑行时长虚高、时间模式下的剖面
被拉成平台。`geo.ts` 的 `computeElapsed` 按「步」判定停留——相邻点时间差 > 15 s 且
位移 < 15 m（开了自动暂停的码表会产生这种大间隔），或常规间隔下步速 < 1.8 km/h
（没开自动暂停、原地仍每秒记录）；连续停留聚成 run，真实时长 ≥ 15 s 的 run 在时间轴上
整体压平。因此骑行时长、平均速度、爬坡用时都是「移动时间」口径（Strava 同口径），
等灯这类几秒的短暂停留仍计入时长；搬运转移（间隔大且位移也大）不会被误压缩。
速度仍按未压缩的原始时间计算——暂停期间速度应趋近 0，用压缩时间会把 GPS 漂移
的几米除以近零的时间差，产生速度尖峰。

**分段着色怎么画。** ECharts 的 `visualMap` 不会给 line 系列的分段上色（实测 piecewise /
continuous 均无效，且显式 `lineStyle.color` 会直接覆盖它）。因此这里按「颜色键」把轨迹点切成
连续段，每个颜色输出一条 series，非本色的位置填 `null`——`connectNulls: false` 会在 null 处
断开，相邻色段的边界点写入两侧以免接缝断线。

每条的填充用同色线性渐变（自上而下衰减到透明）。填充透明度带**饱和度补偿**：去饱和色
（如未分级爬坡的灰蓝）在浅色背景上按同样透明度几乎看不见，因此按颜色饱和度适度抬高其
透明度上限，让各色段的填充视觉重量接近。

**坡度分段为什么要迟滞和最短段长。** 直接拿逐点坡度查区间，会在阈值附近反复横跳——
实测 82 km 的轨迹会切出 220 个碎段（中位长度 54 m，其中 139 段不足 100 m），
既看不清也不符合骑行体感。所以 `analysis/segments.ts` 做两件事：

1. **迟滞**：只有明确越过边界（多出区间宽度约 1/4 的余量）才换区间，边界抖动不再换色；
2. **过短段合并**：把长度不足阈值的段并入更合适的邻居，并反复进行直到没有过短段。

最短段长的默认值按总距离取 `clamp(总长 × 0.005, 150 m, 500 m)`：下限 150 m 是骑行体感
（更短的坡还来不及感觉就过去了），上限 500 m 防止把整条起伏路合并成单一颜色。
实测 82.55 km 轨迹 → 9 段（中位 8.1 km），7.15 km 轨迹 → 5 段（中位 1.1 km）。

**海拔校准的限流。** Open-Meteo 免费额度是 **600 次/分、5000 次/时、10000 次/日，
且按「坐标个数」计费而不是按请求次数**——一次 100 坐标的请求消耗 100 次额度。
实测连发 6 批（600 坐标）后第 7 批必定返回
`429 Minutely API request limit exceeded`。所以在 50 m 间隔下，82.55 km 的轨迹要采样
1536 个点，第 7 批必然失败（7 km 的轨迹只有 143 个点，所以从不出问题）。

因此 `calibration/openmeteo.ts` 做了三件事：

1. **按坐标计费的滑动窗口限流器**：全局单例，预算取 540 坐标/分（留 10% 余量），
   配额不足时等待最早一笔记录滑出窗口再发，而不是硬打；
2. **429 正确处理**：收到 429 就把配额记为「整窗口已满」（服务端此刻确实满了），
   按官方提示等待约一分钟再重试，而不是 400 ms 后立刻重打；有 `Retry-After` 则优先遵循；
3. **采样间隔自适应**：默认按总长度取 `clamp(总长 / 500, 90, 500)`（取整到 10 m），
   使采样点数落在单个限流窗口内。下限 90 m 是因为 DEM 本身就是 90 m 网格，
   比这更密只是插值，不会带来新的地形信息。

面板会在点击前预告本次的采样点数、请求次数与预计等待时间，超额度时提前说明要等多久。

**沿线地名怎么取。** 地名不做逐点反查，而是一次性把轨迹外扩 8 km 范围内的候选全部取回
（`bbox 外扩取固定值`，不随半径滑杆变化），之后的「半径过滤 / 里程投影 / 择优去重」全在
本地算——因此拖动半径、间距不会重新联网。`overpass.ts` 有几个关键设计：

1. **端点轮换 + 退避重试**：Overpass 是公共免费实例，高负载下常回 504。内置 3 个镜像端点，
   按可用性排序轮换，间隔 2/5/10 s 退避，最多 4 轮，另有 70 s 总预算兜底；
2. **镜像健康校验**：数据库还在装载的实例会返回假时间戳并对任何查询回 200 + 空结果，
   必须拦下来，否则会被当成「这一带没有地名」——比报错更糟；
3. **跨会话缓存**：同一条轨迹的候选落在 localStorage（7 天有效），撞上 504 / 429 也还能用；
   若缓存里有「范围完全包含当前 bbox」的更大块，直接复用，完全省掉一次联网；
4. **仅显示中文名**：`name:zh` / `name` 优先，纯英文兜底名（如 "view point"）不展示。

**沿线地名怎么选。** 每个候选先投影到轨迹折线上（`geo.ts` 的 `projectToPath`，按点到折线
的距离算，而不是到采样点，否则弯道内侧的地名会被漏掉），再按类别过半径过滤：行政中心
离路线往往很远（骑车穿过一个区，区政府可能在十几公里外），所以区县/市按 6–8 倍半径纳入，
村庄、景点这类点状地名按 1–1.6 倍；起点与终点附近放宽一倍兜底。之后四步择优：

1. **同名归并**：「大连理工大学（东/西门）+ 主节点」在 OSM 里是 4 个元素，只在沿路径位置
   接近时归并（相隔很远的同名村庄各自保留）；
2. **先钉住起终点**：各取窗口内得分最高的一个放进结果，避免被后面的高分地名用间距挤掉；
3. **打分贪心**：综合得分 = 类别基准 55% + 离路线远近 35% + 知名度（wikidata/人口）10%，
   按得分从高到低接受，相邻标注沿路径距离不足最小间距的跳过；
4. **画图**：地名用散点系列画在曲线上层（只有系列级 `labelLayout` 才支持
   `hideOverlap` 避让，markPoint 不吃这个配置），点击地名放大到该位置。
